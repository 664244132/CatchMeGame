## สรุปหลักการเขียนโค้ด CSS ที่ดี (CSS Code Review Lessons)

**1. การกำหนดขนาดของ Box Model (Box model sizing)**

- **โค้ดที่ดีควรทำ:** ควรใช้ `box-sizing: border-box` เพื่อให้ความกว้างของคอมโพเนนต์ที่ประกาศไว้ ครอบคลุมไปถึงพื้นที่ของ padding และ border ด้วย
- **คำอธิบาย:** วิธีนี้จะช่วยให้คอมโพเนนต์มีขนาดที่คาดเดาได้และสามารถหดตัวเข้าไปในคอนเทนเนอร์ที่แคบกว่าได้โดยไม่ทำให้เกิดปัญหาของล้น (overflow) ที่ไม่คาดคิด การกำหนดขนาดควรเป็นเหมือนข้อตกลงที่ชัดเจน โดยที่เลย์เอาต์รอบข้างไม่ต้องคอยบวกค่า padding และ border เพิ่มเองในใจ

**2. ลำดับความสำคัญและความเฉพาะเจาะจง (Cascade and specificity)**

- **โค้ดที่ดีควรทำ:** ควรใช้คลาสของคอมโพเนนต์และ modifier ที่ระบุชัดเจน เพื่อให้คลาสมีระดับความเฉพาะเจาะจง (specificity) ต่ำและกำหนดขอบเขตได้ดี
- **คำอธิบาย:** การทำเช่นนี้ช่วยให้ผู้รีวิวสามารถดูได้ว่ากฎไหนควบคุมสถานะใดอยู่ โดยไม่ต้องไล่ดูโครงสร้างทั้งหน้าเพจ คุณควรหลีกเลี่ยงการใช้ selector ที่ซ้อนกันลึกๆ, การอ้างอิง ID, และการใช้ `!important` เพื่อแก้ปัญหาซ้ำๆ เพราะจะทำให้การเขียนทับสไตล์ (override) ในอนาคตทำได้ยากและผูกติดอยู่กับโครงสร้าง DOM รูปแบบเดียว

**3. ขอบเขตของการจัดเลย์เอาต์แบบ Flex (Flex layout boundaries)**

- **โค้ดที่ดีควรทำ:** ควรจัดการระยะห่าง (spacing) และการจัดตำแหน่งให้อยู่ภายในคอมโพเนนต์ที่เป็นเจ้าของเลย์เอาต์นั้นๆ โดยแนะนำให้ใช้คุณสมบัติ `gap` ของ flex
- **คำอธิบาย:** หลีกเลี่ยงการใช้ selector ที่บังคับผลักค่า `margin` ไปยัง element ลูกทุกตัว เนื่องจากจะทำให้โครงสร้างเปราะบางเมื่อ element ลูกมีการสลับลำดับ, มีการปัดบรรทัด (wrap), หรือเมื่อมีคอมโพเนนต์ซ้อนอยู่ภายใน

**4. การสร้าง Grid layout (Grid layout tracks)**

- **โค้ดที่ดีควรทำ:** ควรใช้การกำหนด Grid tracks (เช่น การใช้ `minmax` และ `gap`) ในการสร้างคอลัมน์ที่สามารถตอบสนองตามขนาดหน้าจอ (responsive) ได้
- **คำอธิบาย:** ควรให้ grid เป็นตัวจัดการกฎของคอลัมน์แทนการใช้วิธีคำนวณความกว้างเองด้วย `float`, ค่าเปอร์เซ็นต์, หรือการกำหนด `margin` ให้กับ `nth-child` ซึ่งมักทำให้การเพิ่มช่องว่างหรือเปลี่ยนจำนวนคอลัมน์กลายเป็นการต้องเขียนโค้ดใหม่ทั้งหมด

**5. การใช้หน่วยที่รองรับ Responsive (Responsive units)**

- **โค้ดที่ดีควรทำ:** ควรใช้ค่า responsive ที่มีการกำหนดขอบเขตจำกัดเสมอ (เช่น การใช้ฟังก์ชัน `clamp()`)
- **คำอธิบาย:** วิธีนี้ช่วยป้องกันไม่ให้ข้อความถูกย่อจนเล็กเกินไปบนหน้าจอแคบ หรือขยายจนใหญ่เกินไปบนหน้าจอที่กว้างมากๆ โดยรักษาขนาดพื้นฐานของข้อความให้อยู่ในระดับที่อ่านได้เสมอ

**6. ความเปรียบต่างของสีในสถานะต่างๆ (Color contrast states)**

- **โค้ดที่ดีควรทำ:** ควรออกแบบสถานะต่างๆ (เช่น เมื่อนำเมาส์ไปชี้ หรือใช้คีย์บอร์ดโฟกัส) โดยยังคงรักษาความเปรียบต่าง (contrast) ของสีพื้นหน้าและพื้นหลังให้ผู้ใช้สามารถอ่านและมองเห็นได้อย่างชัดเจน
- **คำอธิบาย:** ควรปฏิบัติต่อการเปลี่ยนสถานะทางภาพ (visual states) ให้เป็นเรื่องของ "พฤติกรรม" ไม่ใช่แค่การตกแต่ง หากเปลี่ยนแค่สีแต่มองเห็นยาก ผู้ใช้อาจจะไม่สามารถรับรู้ถึงสถานะที่เปลี่ยนไปได้

**7. การจัดการสถานะและ Focus-visible (State selectors and focus-visible)**

- **โค้ดที่ดีควรทำ:** ควรใช้ `:focus-visible` สำหรับการโฟกัสด้วยคีย์บอร์ด และแยกสไตล์ของสถานะต่างๆ (hover, active, selected) ออกจากกันให้เห็นเด่นชัด
- **คำอธิบาย:** การแยกสถานะทำให้แต่ละการโต้ตอบมีความหมายและมองเห็นได้ ข้อควรระวังที่สำคัญคือ **ห้ามตั้งค่า `outline: none` เด็ดขาด** หากไม่มีการออกแบบสไตล์การโฟกัสอื่นที่มองเห็นได้ชัดเจนมาทดแทน

**8. การใช้ Logical properties**

- **โค้ดที่ดีควรทำ:** ควรใช้ logical properties (เช่น `inline`, `block`, `start`, `end`) สำหรับการเว้นระยะและขอบ แทนการกำหนดทิศทางทางกายภาพแบบตายตัว (`left`, `right`, `top`, `bottom`) เมื่อคุณไม่ได้เจาะจงทิศทางนั้นจริงๆ
- **คำอธิบาย:** วิธีนี้ช่วยให้คอมโพเนนต์สามารถปรับตัวเองให้เข้ากับทิศทางการเขียน (writing direction) ของภาษาที่แตกต่างกันได้ง่ายขึ้น ช่วยประหยัดต้นทุนในการทำ Localization หรือการนำเลย์เอาต์กลับมาใช้ใหม่

**9. การใช้ตัวแปร CSS (Custom properties as design tokens)**

- **โค้ดที่ดีควรทำ:** ควรใช้ Custom properties ในการตั้งชื่อให้กับค่าที่สะท้อนถึงการตัดสินใจในระบบดีไซน์ (Design tokens) เช่น สี, ระยะห่าง, หรือความโค้ง
- **คำอธิบาย:** วิธีนี้ช่วยลดการเขียนค่าตัวเลขลงไปตรงๆ (Magic values) แบบซ้ำซ้อน ซึ่งหากไม่มีตัวแปร เวลาเปลี่ยนดีไซน์แต่ละครั้งจะต้องเสียเวลาค้นหาและแทนที่โค้ด (search-and-replace) เป็นจำนวนมาก

**10. การเคลื่อนไหวและการลดการเคลื่อนไหว (Motion and reduced motion)**

- **โค้ดที่ดีควรทำ:** การใช้แอนิเมชันควรมีจุดประสงค์ชัดเจนเพื่อใช้สื่อสารการเปลี่ยนสถานะ และควรเพิ่มการตั้งค่า `prefers-reduced-motion` เพื่อลดระยะเวลา หรือปรับรูปแบบแอนิเมชันให้เหมาะสมสำหรับผู้ใช้ที่ต้องการลดการเคลื่อนไหว
- **คำอธิบาย:** ไม่ควรบังคับแอนิเมชันเดิมให้แสดงผลกับผู้ใช้ทุกคน หรือซ่อนสถานะที่เปิดใช้งานอยู่ไว้ภายในแอนิเมชันที่ไม่รองรับความต้องการของผู้ใช้งาน แอนิเมชันที่ดีต้องช่วยให้สถานะต่างๆ เข้าใจง่ายขึ้น ไม่ใช่กลายเป็นวิธีเดียวที่ทำให้ผู้ใช้เข้าใจ

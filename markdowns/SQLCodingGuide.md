```markdown
# 📘 แนวทางการเขียนและรีวิวโค้ด SQL ที่ดี (SQL Best Practices)

เอกสารนี้รวบรวมหลักการเขียนโค้ด SQL ที่ดี เพื่อประสิทธิภาพ ความถูกต้อง และความปลอดภัยของข้อมูล

## 1. เลือกดึงเฉพาะคอลัมน์ที่จำเป็น (Explicit SELECT columns)

- **โค้ดที่ดี:** ควร**ระบุชื่อคอลัมน์ที่ต้องการใช้งานจริง ๆ** แทนการพึ่งพารูปแบบตาราง (เช่น การใช้ `SELECT *`)
- **เหตุผล:** ผลลัพธ์ของ Query เปรียบเสมือน API contract การระบุคอลัมน์ชัดเจนจะช่วยรักษาโครงสร้างข้อมูลให้เสถียร ป้องกันชื่อคอลัมน์ซ้ำซ้อน และหลีกเลี่ยงการหลุดรอดของข้อมูลสำคัญ (Sensitive fields) เมื่อมีการแก้ไขโครงสร้าง Schema ในอนาคต

## 2. การจัดการตัวกรองและค่า NULL (Filtering and NULL handling)

- **โค้ดที่ดี:** ใช้**ตัวดำเนินการสำหรับ NULL โดยเฉพาะ (เช่น `IS NULL`)** และการจัดกลุ่มตรรกะ Boolean ให้ชัดเจน (เช่น ใส่วงเล็บให้กับ `AND` หรือ `OR`)
- **เหตุผล:** ค่า NULL ไม่สามารถนำไปเปรียบเทียบความเท่ากันกับสิ่งใดได้ การใช้วงเล็บจะช่วยแก้ปัญหาความกำกวมของลำดับการทำงาน (Operator precedence) และช่วยป้องกันไม่ให้ข้อมูลที่ไม่ต้องการ (เช่น ข้อมูลที่ถูกลบไปแล้ว) หลุดเข้ามาในผลลัพธ์

## 3. ระวังจำนวนแถวข้อมูลที่เปลี่ยนไปจากการ Join (Join cardinality)

- **โค้ดที่ดี:** **ตรวจสอบความสัมพันธ์แบบ one-to-one และ one-to-many เสมอ** ก่อนที่จะไว้ใจผลลัพธ์จากการ Join อาจพิจารณาใช้การรวมข้อมูล (Pre-aggregate) ก่อน แล้วค่อยใช้ `LEFT JOIN` เพื่อให้ข้อมูลหลักยังคงมีจำนวนบรรทัดที่ถูกต้อง
- **เหตุผล:** การ Join เข้ากับตารางที่เป็นฝั่ง Many อาจทำให้จำนวนแถวข้อมูลเพิ่มขึ้นอย่างไม่คาดคิด ซึ่งส่งผลเสียอย่างเงียบ ๆ ต่อการนับจำนวน (Counts) การแบ่งหน้าเว็บ (Pagination) และการสรุปผลข้อมูล

## 4. จัดกลุ่มข้อมูลให้ตรงกับสิ่งที่ต้องการรายงาน (Aggregation and grouping)

- **โค้ดที่ดี:** **ระบุคอลัมน์ใน `GROUP BY` ให้ตรงกับเจตนาของคอลัมน์แบบ Non-aggregated** ที่ปรากฏในคำสั่ง `SELECT` ทุกตัว
- **เหตุผล:** การผสมข้อมูลเวลาดิบ (Raw timestamp) เข้ากับการจัดกลุ่มด้วยสถานะเพียงอย่างเดียว อาจทำให้ระบบฐานข้อมูลทำงานล้มเหลว หรือคืนค่าผลลัพธ์ที่ทำให้เกิดความเข้าใจผิดได้

## 5. เขียนเงื่อนไขให้เป็นมิตรกับ Index (Index-friendly predicates)

- **โค้ดที่ดี:** รักษาให้คอลัมน์ที่มี Index สามารถค้นหาได้รวดเร็ว โดย**หลีกเลี่ยงการใช้ฟังก์ชันไปครอบที่ตัวคอลัมน์**ในฝั่งซ้ายของเงื่อนไขการค้นหา ควรใช้รูปแบบช่วงเวลาแบบ Half-open range แทน
- **เหตุผล:** การนำฟังก์ชันไปครอบตัวคอลัมน์ในทุก ๆ แถว ถึงแม้อ่านง่าย แต่จะไปบล็อกการทำงานปกติของ Index ทำให้สูญเสียประสิทธิภาพการค้นหาในฐานข้อมูล

## 6. ใช้ Transaction มัดรวมการทำงานที่เกี่ยวข้องกัน (Transactions for atomic workflows)

- **โค้ดที่ดี:** **ครอบขั้นตอนการเขียน/อัปเดตข้อมูลหลาย ๆ สเต็ปไว้ใน Transaction เดียว** เพื่อให้ทุกอย่างเสร็จสมบูรณ์หรือล้มเหลวพร้อมกัน (Atomicity)
- **เหตุผล:** หากไม่มี Transaction การล้มเหลวที่คำสั่งใดคำสั่งหนึ่งระหว่างทาง จะทำให้ฐานข้อมูลตกอยู่ในสถานะที่ไม่สมบูรณ์ (Inconsistent state)

## 7. แบ่งขั้นตอนการทำ Migration ให้ปลอดภัย (Migration backfills)

- **โค้ดที่ดี:** **แบ่งการเปลี่ยนแปลงโครงสร้าง Schema ออกเป็นขั้นตอนที่ปลอดภัย** เช่น เริ่มจากเพิ่มคอลัมน์ใหม่ -> ย้อนหลังเติมข้อมูลเดิม (Backfill) ให้ครบ -> แล้วจึงเพิ่มข้อจำกัดความถูกต้อง (Constraints)
- **เหตุผล:** การไปบังคับว่าคอลัมน์ใหม่ต้องห้ามว่างเปล่า (Required) ในขณะที่ข้อมูลเก่ายังไม่มีค่า จะทำให้เกิด Error ทันที การทำ Migration ที่ปลอดภัยจะต้องเคารพและสอดคล้องกับข้อมูลเดิมที่มีอยู่ด้วย

## 8. ใช้ Parameterized Queries ป้องกันการโจมตี (Parameterized queries)

- **โค้ดที่ดี:** **นำค่าที่ผู้ใช้กรอกมารวมเข้าเป็น Parameter (Bound parameters)** เสมอ แทนการนำข้อความไปต่อกันตรง ๆ (String concatenation/Template interpolation)
- **เหตุผล:** เพื่อป้องกันการโจมตีแบบ SQL Injection ค่าที่ผู้ใช้กรอกเข้ามาที่มีเครื่องหมายคำพูด หรือไวยากรณ์ SQL อาจทำให้คำสั่งถูกเปลี่ยนแปลงได้ การใช้ Parameter จะทำให้แน่ใจว่าระบบมองอินพุตเป็นแค่ "ข้อมูล" ไม่ใช่ "คำสั่ง"

## 9. ทำระบบแบ่งหน้าให้เสถียร (Stable pagination)

- **โค้ดที่ดี:** **หลีกเลี่ยงการใช้ Offset pagination แต่นำ Cursors มาใช้** (เช่น ระบุจุดเชื่อมต่อของข้อมูลปัจจุบันผ่าน Timestamp และ ID) และต้องมีค่า Order ที่ให้ผลลัพธ์คงที่ (Deterministic ordering)
- **เหตุผล:** การใช้ Offset กับข้อมูลที่ลำดับไม่เป็นเอกลักษณ์ อาจทำให้เกิดหน้าเลื่อน (Page drift) เวลาที่มีข้อมูลใหม่เพิ่มเข้ามา ซึ่งส่งผลให้แสดงข้อมูลซ้ำ หรือข้ามข้อมูลบางแถวไป

## 10. กำหนดสิทธิ์และความสัมพันธ์ตารางให้ชัดเจน (Schema keys and constraints)

- **โค้ดที่ดี:** วางโครงสร้างตารางด้วย **Primary keys, Foreign keys, Uniqueness และ Check constraints** เสมอ
- **เหตุผล:** เพื่อสร้างการเชื่อมโยง สิทธิ์ความเป็นเจ้าของข้อมูล และรับประกันความถูกต้องของระดับ Schema โครงสร้างข้อมูล

## 11. ตรวจสอบชื่อคอลัมน์ใน Schema ก่อนเขียน SQL (Exact Column Name Verification)

- **โค้ดที่ดี:** ตรวจสอบโครงสร้างตารางจริงจากไฟล์ `database/schema.sql` เสมอก่อนเขียนคำสั่ง `SELECT` หรือ `JOIN`
- **เหตุผล:** เพื่อป้องกันปัญหาการมโนชื่อคอลัมน์ผิดพลาด เช่น ตาราง `public.users` เก็บชื่อผู้ใช้งานไว้ในคอลัมน์ **`display_name`** (ไม่มีคอลัมน์ชื่อ `name`) หากเขียน `u.name` ฐานข้อมูล PostgreSQL จะล้มเหลวด้วยข้อผิดพลาด `column u.name does not exist` การเขียนที่ปลอดภัยควรใช้ `COALESCE(u.display_name, u.email, 'Community Member')` แทน
```

การเขียนเงื่อนไข `WHERE` ให้เป็นมิตรกับ Index (Index-friendly predicates) มีหลักการสำคัญคือ **หลีกเลี่ยงการนำฟังก์ชันไปครอบที่ตัวคอลัมน์ (ฝั่งซ้ายของเงื่อนไข)** เพราะจะไปบล็อกการทำงานปกติของ Index ทำให้ฐานข้อมูลไม่สามารถใช้ Index วิ่งค้นหาข้อมูลได้อย่างรวดเร็ว

จากแหล่งข้อมูลได้ยกตัวอย่างกรณีที่พบบ่อย คือการค้นหาข้อมูลจากคอลัมน์วันที่และเวลา (เช่น `submitted_at`) ซึ่งสามารถนำมาเขียนเป็นคำสั่ง SQL เพื่อให้เห็นภาพได้ดังนี้ครับ:

**❌ โค้ดที่ไม่ดี (ใช้ฟังก์ชันครอบคอลัมน์):**

```sql
SELECT *
FROM reviews
-- สมมติว่ามีการใช้ฟังก์ชันจัดรูปแบบวันที่ครอบลงไปที่คอลัมน์
WHERE DATE_FORMAT(submitted_at, '%Y-%m') = '2026-05';
```

- **เหตุผล:** โค้ดแบบนี้แม้จะอ่านทำความเข้าใจได้ง่าย แต่การใช้ฟังก์ชันจัดรูปแบบไปครอบคอลัมน์ จะทำให้ฐานข้อมูลต้องคำนวณค่านี้ใหม่สำหรับ "ทุก ๆ แถว" ในตาราง ซึ่งเป็นการบล็อกไม่ให้ระบบใช้ Index ที่มีอยู่ได้ ทำให้สูญเสียประสิทธิภาพเมื่อต้องทำงานกับข้อมูลจำนวนมาก

**✅ โค้ดที่ดี (ใช้รูปแบบช่วงเวลาแบบ Half-open range):**

```sql
SELECT *
FROM reviews
-- ปล่อยคอลัมน์ไว้เดี่ยวๆ แล้วใช้เครื่องหมาย >= และ < กับค่าคงที่แทน
WHERE submitted_at >= '2026-05-01' AND submitted_at < '2026-06-01';
```

- **เหตุผล:** การเขียนแบบช่วงเวลาเปิดครึ่ง (Half-open range) โดยปล่อยให้คอลัมน์ `submitted_at` อยู่เดี่ยวๆ โดยไม่มีฟังก์ชันใดๆ มาครอบ จะช่วยให้ฐานข้อมูลสามารถเข้าไปดึงข้อมูลจาก Index ของคอลัมน์นี้มาใช้งานได้โดยตรง (Index seek) ทำให้การค้นหาทำงานได้รวดเร็วและมีประสิทธิภาพอย่างแท้จริง

การจัดการค่า `NULL` ในคำสั่ง `WHERE` มีหลักการที่สำคัญมาก เพราะ **ค่า `NULL` ไม่สามารถนำไปเปรียบเทียบความเท่ากันกับสิ่งใดได้เลย (NULL is not equal to anything)**

จากแหล่งข้อมูลได้อธิบายถึงรูปแบบการเขียนที่ถูกต้องและไม่ถูกต้องในหัวข้อ Filtering and NULL handling ไว้ดังนี้ครับ:

**❌ โค้ดที่ไม่ดี (เปรียบเทียบเท่ากับ NULL และไม่จัดกลุ่มเงื่อนไข):**
ถึงแม้แหล่งข้อมูลจะไม่ได้ให้โค้ด SQL มาโดยตรง แต่อธิบายลักษณะของโค้ดที่แย่ไว้ว่า เป็นการนำค่าไปเปรียบเทียบกับ `NULL` ด้วยเครื่องหมายเท่ากับ (Equality operators) และปล่อยให้ลำดับการทำงานของเงื่อนไข `AND`/`OR` กำกวม ตัวอย่างเช่น:

```sql
SELECT *
FROM reviews
-- ใช้เครื่องหมาย = กับ NULL และไม่มีวงเล็บแยกกลุ่ม AND/OR
WHERE status = 'approved' OR status = 'pending' AND deleted_at = NULL;
```

- **ผลเสีย:** ฐานข้อมูลจะตีความลำดับการทำงาน (Operator precedence) กำกวม ซึ่งอาจทำให้คืนค่าผลลัพธ์เป็นข้อมูลที่ผิดพลาด ไม่มีข้อมูลออกมาเลย หรืออาจมีข้อมูลที่ถูกลบไปแล้วหลุดรอดเข้ามาในผลลัพธ์ได้

**✅ โค้ดที่ดี (ใช้ตัวดำเนินการของ NULL และจัดกลุ่มด้วยวงเล็บชัดเจน):**
โค้ดที่ดีจะต้องใช้คำสั่ง **`IS NULL`** (หรือ `IS NOT NULL`) และจัดกลุ่มเงื่อนไข Boolean (Explicit boolean logic) ด้วยการใส่วงเล็บให้ชัดเจน ตัวอย่างเช่น:

```sql
SELECT *
FROM reviews
-- ใช้วงเล็บจัดกลุ่ม OR ให้ชัดเจน และใช้ IS NULL ในการตรวจสอบ
WHERE (status = 'approved' OR status = 'pending') AND deleted_at IS NULL;
```

- **ผลดี:** การใช้วงเล็บครอบเงื่อนไข `OR` จะทำให้เรามั่นใจว่าฐานข้อมูลจะกรองเฉพาะสถานะที่ต้องการก่อน แล้วจึงค่อยไปเช็กเงื่อนไข `AND deleted_at IS NULL` การเขียนแบบนี้จะช่วยรับประกันว่าข้อมูลแถวที่ถูกลบไปแล้วจะไม่หลุดเข้ามาปะปนในผลลัพธ์อย่างแน่นอน

**💡 คำแนะนำเพิ่มเติมตอนรีวิวโค้ด:**
เวลาที่คุณต้องรีวิวโค้ดที่มีคอลัมน์อนุญาตให้เป็นค่า `NULL` ได้ (Nullable columns) ให้อ่านเงื่อนไข `AND` และ `OR` ทุกตัวโดยจินตนาการว่ามีวงเล็บครอบอยู่เสมอ และต้องตรวจสอบให้แน่ใจว่าผลลัพธ์ที่ได้นั้นตั้งใจจะ "รวม" หรือ "แยก" ค่า `NULL` ออกไป

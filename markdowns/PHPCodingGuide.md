# คู่มือการรีวิวโค้ด PHP: รูปแบบสำหรับการพัฒนาอย่างปลอดภัย

**1. การระบุประเภทข้อมูลที่ชัดเจน (Strict types and return types)**

- **สิ่งที่ควรทำ:** **ประกาศใช้ strict types และระบุประเภทของ parameter รวมถึง return types** ให้ชัดเจนที่บริเวณขอบเขตของฟังก์ชัน (Function boundaries)
- **เหตุผล:** เพื่อทำให้ข้อตกลงของฟังก์ชัน (Contracts) ชัดเจนขึ้น ซึ่งจะช่วยให้นักพัฒนาสามารถดักจับข้อผิดพลาดที่เกิดจากการแปลงชนิดข้อมูลแบบอัตโนมัติ (Coercion bugs) ได้ตั้งแต่เนิ่นๆ แทนที่จะต้องมานั่งเดาว่าฟังก์ชันรองรับข้อมูลประเภทใดบ้าง

**2. การตรวจสอบและคัดกรองข้อมูลนำเข้า (Input validation and filtering)**

- **สิ่งที่ควรทำ:** **ตรวจสอบข้อมูลที่ได้รับ (Request input) ตั้งแต่จุดเริ่มต้นรับข้อมูล** และควรหยุดการทำงานพร้อมตอบกลับ HTTP ที่ชัดเจนหากข้อมูลไม่ถูกต้อง ก่อนที่จะส่งต่อไปยังโค้ดส่วนฐานข้อมูล, โดเมน หรือเทมเพลต
- **เหตุผล:** ตัวแปรประเภท Superglobals ถือเป็นขอบเขตที่ไม่สามารถเชื่อถือได้ เราควรแปลงให้อยู่ในรูปแบบค่าที่มีประเภทชัดเจน (Normalize) เสียก่อน เพื่อไม่ให้โค้ดในชั้นที่ลึกลงไปต้องจัดการกับข้อมูลที่ไม่พึงประสงค์

**3. การหลีกหนีข้อมูลเพื่อป้องกัน XSS (Output escaping for XSS)**

- **สิ่งที่ควรทำ:** **ทำ Output Escaping กับข้อมูลที่ไม่น่าเชื่อถือเสมอ** เมื่อต้องเรนเดอร์เป็น HTML โดยพิจารณาตามบริบท (เช่น ข้อความธรรมดา, Attributes หรือ JavaScript)
- **เหตุผล:** เพื่อป้องกันไม่ให้ข้อมูลจากผู้ใช้ถูกตีความหมายว่าเป็น Markup หรือถูกรันเป็นสคริปต์บนหน้าเว็บ (Cross-Site Scripting)

**4. การใช้ Prepared Statements สำหรับฐานข้อมูล (PDO prepared statements)**

- **สิ่งที่ควรทำ:** **ใช้ Prepared Statements และผูกค่าข้อมูล (Bound values)** เข้ากับคำสั่ง SQL แทนการนำค่าที่ได้จาก request มาต่อสตริง (Interpolate) ตรงๆ
- **เหตุผล:** เพื่อแยกโครงสร้างคำสั่ง SQL ออกจากค่าของข้อมูลอย่างชัดเจน ซึ่งนอกจากจะช่วยป้องกัน SQL Injection แล้ว ยังทำให้อ่านจุดประสงค์ของคิวรีและชื่อพารามิเตอร์ได้ง่ายขึ้นตอนรีวิวโค้ด

**5. การแฮชและการตรวจสอบรหัสผ่าน (Password hashing and verification)**

- **สิ่งที่ควรทำ:** **ใช้ API สำหรับจัดการรหัสผ่านของ PHP โดยตรง (`password_hash` และ `password_verify`)**
- **เหตุผล:** ไม่ควรประดิษฐ์ตรรกะการแฮช/สร้าง Salt ของตัวเอง หรือใช้ฟังก์ชันแฮชทั่วไปที่ทำงานเร็ว (Fast general-purpose hashes) เพราะ API ของ PHP ถูกออกแบบมาเพื่อรหัสผ่านโดยเฉพาะ และสามารถเก็บข้อมูลอัลกอริทึมรวมถึงค่าความยาก (Cost) ไว้ในตัวแฮชได้เลย

**6. การจัดการเซสชันและคุกกี้ (Session handling and cookies)**

- **สิ่งที่ควรทำ:** **กำหนดค่า Flags ของคุกกี้อย่างรอบคอบ และสุ่ม Session ID ขึ้นมาใหม่ (Regenerate)** ทุกครั้งเมื่อสถานะการยืนยันตัวตนของผู้ใช้มีการเปลี่ยนแปลง เช่น ตอนเข้าสู่ระบบ
- **เหตุผล:** การเปลี่ยนแปลงการยืนยันตัวตนคือการเปลี่ยนแปลงขอบเขตของเซสชัน การจัดการเรื่องนี้ให้ชัดเจนจะช่วยป้องกันช่องโหว่และการสวมรอย (Session Hijacking)

**7. การจัดการข้อผิดพลาดและข้อยกเว้น (Error handling and exceptions)**

- **สิ่งที่ควรทำ:** **ดักจับ Exceptions ที่ขอบเขตการทำงานที่ชัดเจน (เช่น Front controller) บันทึกรายละเอียดลง Log** และส่งคืนเพียงข้อความแจ้งเตือนที่ปลอดภัยต่อผู้ใช้งาน (Generic response)
- **เหตุผล:** เพื่อแยกระหว่างข้อมูลสำหรับการวิเคราะห์ปัญหาของนักพัฒนา ออกจากการแสดงผลฝั่งผู้ใช้ ป้องกันไม่ให้ข้อความ Error ลึกๆ (Raw exception messages) หลุดไปแสดงผลบนเบราว์เซอร์

**8. การจัดการโครงสร้างไฟล์ด้วย Autoloading และ Namespaces**

- **สิ่งที่ควรทำ:** **ใช้ Namespaces และให้โหลดคลาสแบบอัตโนมัติ (Autoloaded classes)** ผ่านการทำ Dependency injection
- **เหตุผล:** ทำให้โครงสร้างไฟล์ ความเป็นเจ้าของ และความสัมพันธ์ (Dependencies) ของคลาสต่างๆ ชัดเจนยิ่งขึ้น ดีกว่าการพึ่งพาลำดับของคำสั่ง `require_once` ต่อๆ กันแบบลูกโซ่ หรือพึ่งพา Global state

**9. การจัดการการตั้งค่าและความลับของระบบ (Configuration and secrets)**

- **สิ่งที่ควรทำ:** **โหลดค่าการตั้งค่าต่างๆ จากตัวแปรสภาพแวดล้อม (Environment)** และตั้งให้ระบบหยุดการทำงานอย่างชัดเจนตอนเริ่มต้น (Startup) หากหาค่าความลับ (Secrets) ที่จำเป็นไม่พบ
- **เหตุผล:** ข้อมูลความลับควรทำงานในฐานะ Runtime configuration ไม่ควรถูกฮาร์ดโค้ด (Hardcode) หรือคอมมิตเก็บไว้ในไฟล์ลอจิกของแอปพลิเคชัน และไม่ควรให้ค่าจากฝั่งผู้ใช้ (Request value) มาเปลี่ยนแปลงการตั้งค่าของโครงสร้างพื้นฐานได้

**10. การแยกตรรกะออกจากเทมเพลต (Separating logic from templates)**

- **สิ่งที่ควรทำ:** **แยกการจัดการ Request และการดึงข้อมูลฐานข้อมูลออกจากไฟล์เทมเพลต** โดยไฟล์เทมเพลตควรทำหน้าที่แค่เรนเดอร์ข้อมูลจาก View model ที่เตรียมไว้ให้แล้ว
- **เหตุผล:** เพื่อให้โค้ดแสดงผลมีขนาดเล็กและง่ายต่อการรีวิว หากไฟล์ใดไฟล์หนึ่งทำหน้าที่ทั้งรับค่า, คิวรี SQL และเรนเดอร์ผลลัพธ์ ควรจะแยกมันออกจากกัน (Separation of concerns)

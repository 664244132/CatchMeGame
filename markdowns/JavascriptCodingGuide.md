# สรุปแนวทางการเขียน JavaScript ที่ดี (JavaScript Code Review Patterns)

### 1. Strict equality and nullish checks (การตรวจสอบความเท่ากันอย่างเข้มงวดและการจัดการค่า Nullish)

- **ควรทำ:** ใช้การเปรียบเทียบค่าแบบเข้มงวด (Strict equality `===`) และใช้ Nullish coalescing (`??`) เมื่อต้องการให้ใช้ค่าสำรอง (Fallback) เฉพาะในกรณีที่ค่าเป็น `null` หรือ `undefined` เท่านั้น
- **คำอธิบาย:** การใช้การเปรียบเทียบแบบหลวมๆ (Loose equality) หรือตัวดำเนินการ `||` อาจทำให้เกิดบั๊กซ่อนเร้นที่ระบบไม่สามารถแยกแยะความแตกต่างระหว่าง "การไม่มีข้อมูล" กับ "ค่า Falsy ที่ถูกตั้งใจกำหนดไว้" (เช่น `0` หรือ `false`) ได้ ซึ่งอาจทำให้สูญเสียค่าที่ถูกต้องไป

### 2. Guard clauses (การใช้เงื่อนไขแบบคืนค่ากลับให้เร็วที่สุด)

- **ควรทำ:** ใช้การ `return` ออกจากฟังก์ชันตั้งแต่เนิ่นๆ (Early returns) สำหรับข้อมูลที่ไม่ถูกต้องหรือไม่ผ่านเงื่อนไข เพื่อให้เคสเหล่านี้อยู่นอกเส้นทางการทำงานหลักของระบบ
- **คำอธิบาย:** การใช้ Guard clauses ช่วยลดการเขียนเงื่อนไขซ้อนกันลึกๆ (Deep branching) ทำให้โค้ดในการทำงานปกติ (Happy path) ไม่มีความซับซ้อน อ่านง่าย และเพิ่มเงื่อนไขในอนาคตได้ง่ายขึ้น

### 3. Validating data boundaries (การตรวจสอบข้อมูลที่จุดเชื่อมต่อ)

- **ควรทำ:** ตรวจสอบข้อมูลจากภายนอก (เช่น ข้อมูลจาก API, Storage หรือ Message payloads) ที่บริเวณ "ขอบเขตรับข้อมูล" ทันทีก่อนที่โค้ดส่วนอื่นจะนำข้อมูลนั้นไปใช้ หรือเข้าไปอ่านฟิลด์ที่ซ้อนอยู่ด้านใน
- **คำอธิบาย:** การทำเช่นนี้ช่วยให้เมื่อเกิดปัญหาข้อมูลผิดรูปแบบ ระบบจะคืนค่าสถานะล้มเหลว (Clear failure) ที่ชัดเจนทันที แทนที่จะปล่อยให้ข้อมูลผ่านเข้าไปจนเกิดเป็น Runtime Error ที่ไม่เกี่ยวข้องในภายหลัง

### 4. Naming side effects (การตั้งชื่อฟังก์ชันที่เปลี่ยนค่าดั้งเดิม)

- **ควรทำ:** ตั้งชื่อฟังก์ชันให้ผู้เรียกใช้ทราบอย่างชัดเจนหากจะมีการเปลี่ยนแปลงค่าในข้อมูลเดิม (In-place mutation) หรือถ้าไม่อยากให้สับสนควรให้ฟังก์ชันคืนค่ากลับมาเป็นข้อมูลชุดใหม่เสมอ
- **คำอธิบาย:** บางฟังก์ชันอาจมีชื่อที่ดูไม่มีพิษมีภัย แต่แอบแก้ข้อมูลที่ส่งเข้ามา (Mutate state) สิ่งนี้อาจทำให้โค้ดส่วนอื่นที่ใช้ข้อมูลอ้างอิงชุดเดิมทำงานผิดพลาดได้

### 5. Array transformations (การแปลงโครงสร้าง Array)

- **ควรทำ:** ใช้เมธอดของ Array เช่น `filter`, `map`, และ `reduce` เพื่อแปลงข้อมูล แทนการลูปเข้าไปปรับเปลี่ยนข้อมูลดั้งเดิม
- **คำอธิบาย:** การใช้เมธอดเหล่านี้ทำให้โค้ดอ่านง่ายเป็นลำดับขั้น (เหมือนท่อส่งข้อมูล Pipeline) และช่วยหลีกเลี่ยงการเปลี่ยนแปลงลำดับใน Array หรือเปลี่ยนแปลง Object ภายในโดยไม่ได้ตั้งใจ (Accidental mutation)

### 6. Async error handling (การจัดการข้อผิดพลาดแบบ Asynchronous)

- **ควรทำ:** ก่อนที่จะเริ่มนำข้อมูลไปแปลงผล (เช่นแปลงเป็น JSON) ควรตรวจสอบให้แน่ใจก่อนว่าเครือข่ายไม่ล้มเหลวและสถานะการตอบสนอง (HTTP Response status) สำเร็จครบถ้วน
- **คำอธิบาย:** การตั้งสมมติฐานว่าทุก Request จะสำเร็จเสมอ (Happy path) และสามารถอ่านเป็น JSON ได้ จะทำให้พฤติกรรมความล้มเหลวที่สำคัญไปปรากฏเป็น Unhandled exceptions โค้ดที่ดีต้องแยกรับมือกรณีออฟไลน์หรือเซิร์ฟเวอร์แจ้ง Error ได้อย่างเป็นระบบ

### 7. Promise concurrency (การจัดการการทำงานแบบขนาน)

- **ควรทำ:** ใช้ `Promise.all` เพื่อเริ่มต้นทำงานแบบ Asynchronous ที่ไม่มีความเกี่ยวข้องกันไปพร้อมๆ กัน (Concurrent work) และใช้ `await` ลำดับถัดกันไปเฉพาะกับงานที่ต้องใช้ผลลัพธ์ต่อเนื่องกันจริงๆ เท่านั้น
- **คำอธิบาย:** การสั่งให้ Request แต่ละตัวรอตัวก่อนหน้าให้เสร็จสิ้น (Sequential await) ทั้งๆ ที่ข้อมูลไม่เกี่ยวข้องกัน จะเป็นการเพิ่มเวลาความหน่วง (Latency) ของแอปพลิเคชันโดยไม่จำเป็น

### 8. Event listener cleanup (การทำความสะอาด Event listener)

- **ควรทำ:** คืนค่าเป็นฟังก์ชันสำหรับทำความสะอาด (Cleanup function) เสมอ เมื่อมีการแนบ Listener, Timer หรือ Observer โดยการเก็บตัวอ้างอิงของ Handler เดิมเอาไว้
- **คำอธิบาย:** ทุกครั้งที่มีการตั้งค่า Listener ควรมีวิธีการที่จะเอาออกเมื่อ UI นั้นไม่ได้ใช้งานแล้ว หากไม่จัดการอาจทำให้เกิดการทำงานซ้อนทับกัน (Duplicate shortcuts/behavior) สะสมอยู่ในแอปพลิเคชันได้

### 9. Module boundaries and globals (การจัดการขอบเขต Module และ Global state)

- **ควรทำ:** ส่งพฤติกรรมที่ใช้ร่วมกันผ่านตัวแปรแบบ Dependencies (เช่น ส่งข้อมูลเข้า Module หรือเข้าฟังก์ชันโดยตรง) เพื่อไม่ให้มีการผูกมัดค่าติดไว้เป็นตัวแปรแบบ Global หรือเขียนลงใน `window` และ `localStorage` โดยตรง
- **คำอธิบาย:** การมีสถานะใน Global (เช่น `window`) เปิดโอกาสให้โค้ดในส่วนอื่นสามารถเปลี่ยนแปลงค่าได้อย่างอิสระ การรวมฟังก์ชันต่างๆ ไว้ภายใต้ API ขอบเขตของ Module จะช่วยให้ทำการทดสอบโค้ดง่ายขึ้นและจัดการได้ชัดเจน

### 10. Dates and time zones (การจัดการวันที่และเขตเวลา)

- **ควรทำ:** ใช้ API สำหรับการจัดรูปแบบตามมาตรฐาน เช่น `Intl` ที่ระบุเขตเวลา (Time zone) และ Locale ที่เจาะจงเสมอ เพื่อแสดงวันและเวลา แทนการบวกหรือลบเวลาด้วยการคำนวณเอาเอง
- **คำอธิบาย:** วันที่และเวลามักจะทำงานได้ดีในเครื่องของผู้พัฒนา แต่อาจเกิดปัญหาที่วัน/เดือนเปลี่ยนไปได้เมื่อใช้งานจริงผ่าน Time zone ต่างๆ ของผู้ใช้แต่ละคน ดังนั้นควรระบุเขตเวลาการแปลงวันที่ให้ชัดเจนแทนการปล่อยให้ตัวแปรแวดล้อมระบบตั้งค่าโดยอัตโนมัติ
